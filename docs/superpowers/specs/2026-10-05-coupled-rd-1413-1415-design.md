## Goal and boundary

Define one lifecycle for an owner-authorized protected operation: authenticated ingress, authority-bound secret admission, protected byte custody, verified use, authorized release, cleanup, and safe reuse. RD-1413, RD-1414, and RD-1415 are consecutive gates over the same request and allocation, not independent features.

The end state must not expose plaintext to an untrusted outer host kernel or hypervisor. Amazon Linux is the primary server target. Windows 10 is a client/remote-only target for protected requests; it must not silently fall back to local plaintext processing. The exact Amazon Linux confidential-compute profile and its remaining trusted computing base (TCB) are not selected by this draft. This draft does not claim protection from a guest kernel that remains inside the selected TCB; the owner must explicitly decide whether that guest kernel is trusted. If the threat requirement includes a compromised guest kernel, or the attested profile is unavailable, mismatched, or unverifiable, the protected operation refuses until a platform boundary that satisfies that requirement is selected and demonstrated.

The governed `/secure` path is the intended V1 route shape, not a claim that a qualifying route is loaded today. The current `POST /auth/verify` example uses a fixture hash; the separate `verifyPassword.fungi` example reads a named secret but is not bound to that route or to a source-proven object/version grant. Until the owner names a real operation and its object, V1 stays non-authorizing.

## Confirmed owner decisions

- **Owner-approved (2026-10-05):** ECC/RAS is a host reliability layer. It does not authorize callers, authenticate bytes, prove freshness, prevent malicious mutation, or prove erasure.
- **Owner-approved (2026-10-05):** Galerina uses a bounded protected staging-and-verification lifecycle. A second plaintext copy is not the integrity or zero-trust mechanism.
- Fungi owns authorization decisions, secret-byte custody, leases, and cleanup semantics. TypeScript may be a minimal host adapter for framing, transport, and invoking a loaded Fungi runtime; it may not decide authorization or hold plaintext in the protected path.
- A refusal, timeout, crash, unknown state, malformed status, or uncertain external effect is an explicit terminal outcome for that attempt. There is no fast-path fallback that weakens the protected policy.
- A private Signet is authority; a Wax Seal is a terminal, non-authorizing receipt. Neither a receipt nor a graph/index projection may mint, widen, restore, or replay a live grant or capability.
- Graph/index data is a locator and reconciliation projection only. It is not a grant, runtime capability, cleanup acknowledgement, or authority to release/reuse memory.

revalidated at this checkout.

The discriminating residual is narrow but security-relevant: after the raw
consumer callback receives a `Uint8Array`, it can catch a nested-access
refusal and continue reading/copying bytes already in its possession. The
outer request fails with 500 and the gate-owned staging buffer is wiped, but
the consumer copy survives. This is not evidence of a successful response
bypass or repeated provider acquisition. It means a request-level failure
latch cannot revoke plaintext already exposed to arbitrary same-process
callback code.

**Design constraint to carry forward (proposed; not separately approved):**
the protected Fungi/runtime boundary must not hand an unrestricted plaintext
view to arbitrary host callback code. A lease/operation handle, if selected,
must be opaque and object/version-bound; all secret-dependent effects and
authorized release must be mediated inside the protected runtime. Terminal
refusal must invalidate that operation before any later effect or release.
No wrapper token in TypeScript can revoke a copy already made from exposed
bytes. If the runtime cannot enforce that mediation, refuse the protected
operation; do not claim cleanup or HTTP 500 retracts a disclosure.

This finding does not change the already scoped owner decision for ECC/RAS and
bounded protected staging, and does not approve the complete v1.1 draft or
authorize implementation. The real `/secure` route, owner/version grant,
provider/key owner, protected runtime and recipient/release owners remain open.

### Revocation versus provider-open — mechanism remains an owner decision

The advisory Grok follow-up (`response-9dc4b13e-cf41-4413-b687-c7900bdcc3de`)
and independent Astra review `01a10ecc-d545-7f20-9367-97e5d76b3f2a` agree that
a final local `has()`/revocation read followed by a separate provider call does
not order revocation against provider-open. Astra's result is **PARTIAL** and
advisory; it verifies the source pins below, not a deployed runtime. No
mechanism below is established in the current implementation.

Use these event meanings in any future proof: `R` is effective revocation at
the enforcing authority; `O` is the first protected provider effect that can
yield secret bytes (including key use, object-byte acquisition, or protected
object allocation); `D` is the irreversible recipient write or storage commit.
Count attempted calls separately from successful protected effects. A wrapper
timestamp is not a linearization receipt.

| Candidate mechanism — not selected | Minimum condition for the claim | Residual/false-proof control |
|---|---|---|
| Shared lock or lease (M1) | Revocation and every opener use the same exclusion domain; the grant remains protected through actual `O`; revocation cannot become effective until active holders finish or are fenced. | A lease alone is insufficient if a paused holder can resume after revocation. `O < R` may succeed and then be revoked; require and record that order rather than claiming both events cannot succeed. Test revoke-first and open-first contention. |
| Atomic revocation-aware open (M2) | The authoritative grant-validity transition and all effects constituting actual `O` share one serialized operation. | A local check/CAS/reservation followed by separate provider I/O, key use, or allocation recreates the gap. Count those effects on both success and error/partial paths. |
| Provider fencing (M3) | The provider enforces the current authoritative epoch at actual `O`; the sink enforces equivalent authority at `D`; all paths are fenced. | A signed token or provider's highest-token-seen cache alone is insufficient when revocation is not visible. Test stale-token use after revoke without first delivering a newer token and reject unfenced paths. |

The minimum discriminating schedules are: **A**, complete `R`, then attempt `O`—
expect refusal, zero successful protected opens/key uses/object-byte acquisition
and zero `D`; **B**, establish `O < R < D`—classify the open as pre-revocation,
write no sink after `R`, do not retry-open, and keep all acquired/staged/scratch
bytes charged or quarantined pending positive cleanup; **C**, establish
`O < D < R` as an allowed control and record the disclosure as pre-revocation.
Pause a check-then-open candidate between its check and actual `O`, complete
`R`, then resume it; that unsafe candidate must fail A. Instrument the enforcing
provider and actual sink, including partial/failing calls; a disconnected or
always-zero test observer must fail C. If the enforcing boundary has no such
observable ordering record, the test and implementation claim remain
`NOT_VERIFIABLE`.

These are proposed proof obligations, not a choice of M1/M2/M3 or evidence that
the present TypeScript gate, a Fungi runtime, provider, or sink implements them.

## Source-confirmed object/version binding gap

The current provider seam is name-based. The separately pinned coupled review and synthetic replay show that replacing the bytes behind a provider name between presence checking and acquisition can still deliver staged bytes and return success. This is a synthetic counterexample, not a production exploit. A presence check does not prove the bytes belong to the authorized object/version. V1 acquisition must atomically bind canonical source object/version, provider/key owner, generation-bound grant, and authenticated exact bytes; otherwise it refuses. The regression must replace a same-name object/version after admission and prove zero consumer or sink effect.

## Plaintext and key custody map — required before implementation

The route contract must name every component that can materialize plaintext or a decryption key: provider/key owner, decrypting provider endpoint, ingress terminator, protected staging arena, Fungi runtime and scratch, output encryptor, recipient endpoint, and any storage adapter. Each such component must be inside the accepted measured TCB or be a separately approved protected endpoint. Bind ingress session, provider/key release, Fungi operation, content identity, incarnation fence, output encryption, and recipient channel to one operation/grant. A correctly attested application runtime does not compensate for an outer-host provider or output adapter that sees plaintext. Any unbound terminator, key, endpoint, or custody edge refuses. The outer host may transport ciphertext, opaque handles, and bounded non-secret status only.

For a Windows 10 remote client, V1 must explicitly classify which user-originated inputs and authorized results may be plaintext at that endpoint. Provider secrets and decryption keys never move to an unmeasured Windows process. If the owner requires that no protected input or result exist as plaintext on Windows, that client cannot be the plaintext recipient; send only ciphertext or an opaque reference. Remote computation alone does not make local display/input memory confidential.

## Coupled lifecycle

Each request and allocation has a unique request ID, opaque allocation ID, and non-reusable generation. Each transition is monotone. Fields required by a transition are explicit and validated; absent, null, NaN, infinite, negative, fractional, overflowing, contradictory, stale, or unknown values refuse and retain/quarantine the charge.

## Shared authority, state, and graph invariants

1. **Authority, grant, and receipt are distinct.** Private Signet authority is held by its designated owner and never crosses into a graph, adapter, or receipt. A designated issuer may create the one-attempt operation grant only under an explicit owner-approved delegation; runtime attestation alone does not grant minting authority. The protected Fungi runtime validates/consumes that grant and may derive only a non-widening lease bound to principal, operation, object/version, provider/key owner, size bound, and recipient. A Wax Seal is terminal evidence only; replaying it cannot mint, widen, restore, or replay a grant or capability.
2. **Hallmark is a consistency binding, not authority.** Compute it server-side after admission over canonical `(operation-id, policy-id, governed-route-id, grant-generation, runtime-measurement, recipient)` values. Never accept a caller-provided hallmark or Boolean as authorization. Any cross-route, cross-policy, measurement, generation, or recipient mismatch refuses; a fast implementation cannot bypass or downgrade the governed `/secure` policy.
3. **One source of truth for lifecycle transitions.** The protected Fungi runtime maintains the authoritative finite state and generation under its protected boundary. A derived graph may project opaque IDs, generation, bounded lengths, transition sequence, provenance, and cleanup status; consumers must not use that projection to authorize access, release, or reuse.
4. **Tamper evidence is not authority.** Runtime events must be integrity-protected and ordered under a stated key/root and monotonic sequence. Missing, reordered, duplicated, truncated, stale, or unverifiable events make the derived state unknown and block release/reuse. A valid event chain still cannot substitute for Signet authority, an operation grant, or cleanup acknowledgement from the actual owner of each region.
5. **Complete mediation is a prerequisite to cleanup claims.** Every alias, borrow, derived buffer, parser/crypto scratch area, ABI mapping, provider copy, output buffer, and transfer boundary must be either prohibited or registered and mediated before it can exist. An empty graph or zero count does not prove no hidden copy exists.
6. **Closed status vocabulary.** State is a validated tagged enum, not a nullable Boolean. Counts and extents are bounded safe integers with checked arithmetic. `UNKNOWN`, `REFUSED`, `TIMED_OUT`, `CRASHED`, `WIPE_FAILED`, `WIPE_ACK_OK`, `CLEANUP_COMPLETE`, and `DISCLOSED` remain distinct states; only the defined positive cleanup transition releases charge.
7. **Atomic revocation ordering.** A final “not revoked” read followed by provider-open or sink-write is insufficient. The provider/open path and revoker must share a documented linearization mechanism (e.g. one atomic revocation-aware operation, a shared exclusion lease spanning the protected transition, or a provider-enforced fencing epoch). The mechanism must be enforced at both open and delivery where required. No such primitive is asserted to exist in the current source.
8. **ECC/RAS and attribution.** ECC/RAS is reliability telemetry only. A corrected fault touching staged bytes invalidates the previous byte-authentication result; authenticate the exact post-correction bytes again or refuse. If a fault can be reported after affected data/control state has influenced computation or an irreversible effect, invalidate all dependent computation/output, authorization decisions, fence/replay state, budget accounting, cleanup acknowledgements, and recovery records within the uncertainty scope. Re-authentication cannot rehabilitate a stale result or a possibly corrupted control decision. Recompute only through a fresh authorized attempt from clean re-admitted bytes, or refuse. The selected profile must prevent affected results from crossing an irreversible boundary before required fault containment; otherwise that profile is not admitted for V1. A fault reported after an effect is recorded as disclosed/unknown truthfully, never as zero release. Deferred, poisoned, uncorrectable, fatal, or unattributed status blocks use/release/reuse. If affected regions cannot be proven, quarantine the entire protected arena/incarnation. The controller must not rely solely on control metadata that the same fault may have corrupted. Host “healthy/corrected” flags are untrusted unless bound to the selected attested TCB; absent telemetry is `UNKNOWN`, never healthy and never a cleanup acknowledgement. Scrubbing is not erasure; a crash may interrupt cleanup.
9. **Restart and rollback freshness.** A rollback-resistant fencing epoch/high-water authority must live outside state restored with a guest snapshot. Restored leases, generations, replay windows, nonces, and receipts are stale until reconciled against that authority; old and new incarnations cannot both operate. If the authority is unavailable or cannot distinguish incarnations, refuse protected use and release.
10. **Memory reuse.** Reuse requires capability retirement, zero outstanding mediated borrowers, positive per-region wipe acknowledgements, authoritative `CLEANUP_COMPLETE`, extent retirement/unmap where supported, and a fresh fenced generation. Unknown or wrapped generation refuses; no eviction or reuse under pressure.
11. **Terminal failure linearization.** A terminal refusal invalidates authority for every effect not yet linearized, including work admitted or queued while the operation was live. The selected runtime must serialize the terminal transition against computation effects, storage commit and recipient release; checking the handle only before enqueue is insufficient. Effects that linearized earlier are accounted as disclosed/committed and cannot be represented as rolled back or erased. If the runtime cannot enforce and observe this ordering, keep the operation non-authorizing.
12. **Input-use authority and output authority are separate.** The consumed secret/input lease authorizes only its bounded computation and never survives as commit/release authority. A distinct output-only capability may exist only when the same current grant explicitly authorizes the exact result class and recipient; it cannot read, reacquire, or rederive secret bytes. Terminal failure/revocation is serialized against consuming that output capability at the effect boundary. If the transition cannot be enforced, refuse release.

## Error, retry, and recovery contract

- Every path has an explicit exit: accept, refuse, quarantine/unknown, or confirmed terminal completion. A caught provider, parser, crypto, callback, audit, or sink failure cannot turn the same request back into success.
- Pre-acquisition refusal has zero provider opens, zero protected allocations beyond the separately bounded pre-admission allowance (handshake, framing, authentication/parser scratch, and metadata), and zero sink writes.
- Process restart, snapshot restore, clone, migration, or rollback cannot restore a grant, lease, replay window, nonce counter, or authority epoch. Reconcile against an independently fresh fencing authority; if it is unavailable, stay `UNKNOWN` and refuse.
- After acquisition starts, any uncertainty retains the charge and quarantine. Do not retry under the same grant/request ID unless a named recovery authority proves idempotence and reconciles whether disclosure occurred.
- If revocation linearizes before open, open count must remain zero. If open linearizes first but revocation wins before delivery, no sink write may follow; already-open bytes remain charged/quarantined and are not represented as erased. If delivery linearizes before revocation, record the pre-revocation disclosure exactly; revocation cannot retroactively erase it.
- Audit failures are not swallowed into success. Durable audit/recovery must distinguish not-attempted, refused, acquired, verified, delivered, unknown-disclosure, cleanup-pending, and cleanup-complete without recording plaintext or credentials.

## Performance and ECC policy

No duplicate plaintext copy is added just to imitate ECC. Use one bounded protected quarantine allocation and authenticate/validate in place where the selected runtime and crypto primitive permit it. If a primitive necessarily requires scratch, include that scratch in the explicit reserved budget and wipe/retire it under the same lifecycle.

Measure latency, throughput, peak protected bytes, scratch, quarantine residence time, RAS events, and refusal rates on the exact approved Amazon Linux profile. The verification step may use a separately budgeted region only if it cannot alias or modify the active consumer region and the operation's grant covers the relationship; it remains protected and is still wiped/retired. No performance target is invented here. The security floor is not lowered to meet a speed target; if the bound cannot be met, refuse or require a separately approved policy revision.
