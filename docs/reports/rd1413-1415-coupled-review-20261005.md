## ECC analogy: hardware reliability versus adversarial integrity

ECC is useful, but it is not an authorization or hostile-writer defense. Linux
EDAC distinguishes corrected, uncorrected, deferred, and fatal hardware errors;
memory scrubbing uses ECC to detect/correct media errors and can isolate affected
pages. Those controls address accidental hardware faults and RAS. They do not
prove that application bytes were authorized, well-formed, fresh, or untouched
by malicious software. See the [Linux EDAC error model](https://www.kernel.org/doc/html/v6.15/driver-api/edac.html),
[Linux memory-scrub behavior](https://www.kernel.org/doc/html/latest/edac/scrub.html),
and [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final) for authenticated
encryption/tag verification.

**Owner-approved design direction (2026-10-05):** use ECC/RAS as a host
reliability layer and a bounded protected staging-and-verification protocol in
Galerina; do not treat ECC or a second plaintext copy as zero-trust protection.
This approves the direction, not the concrete implementation contract. The
following design details remain proposed and need source/runtime validation:

1. Hardware ECC/RAS remains a platform reliability layer, not an authorization
   or hostile-writer control. Corrected data still passes ordinary
   authentication, authorization, and validation. Deferred/poisoned data is
   not success; affected protected regions stay unavailable. Define fault
   attribution and containment: retire the affected region, or a broader scope
   when attribution is unknown. Do not trust an out-of-TCB healthy Boolean or
   silence as proof that memory is safe. Fatal interruption may prevent
   software cleanup or a final response, so recovery must preserve uncertain
   cleanup/disclosure state instead of inferring a successful wipe. Scrubbing
   is not secret erasure.
2. Put untrusted input in one bounded quarantine region within the approved
   protected boundary. Keep tentative decrypted plaintext inaccessible until
   authentication succeeds. Authenticate the exact bytes and canonical context
   (request/operation, object version, grant, length, freshness, recipient as
   applicable), then validate format, bounds, and current authorization before
   any protected effect. An authentication tag detects tampering relative to
   its key/context; it does not itself grant current authority, prevent replay,
   or validate format.
3. Promotion atomically consumes quarantine authority and exposes only the
   same authenticated, authorized bytes through one short-lived, Fungi-owned
   immutable/opaque lease. Every alias must be unable to mutate the bytes or
   bound context through the final permitted read; if this cannot be proved,
   refuse before consumer effects. A second plaintext copy is not the
   integrity/zero-trust mechanism. Bound quarantine retention and all
   verification buffers.
4. Reserve limits for bytes, crypto/parser scratch, time, concurrency,
   metadata, and output before doing work. On malformed input, failed
   authentication, refusal, timeout, or completion, retire capability authority
   before waiting for borrowers to quiesce and cleanup. Charge quarantined
   allocations until authoritative cleanup acknowledgement; reuse only after
   all mediated views are quiescent, cleanup is acknowledged, and a fresh
   generation is assigned. Refuse generation wrap. Exhaustion denies; unresolved
   allocations are not evicted or reused.
5. Restart, migration, or rollback must not resurrect leases, replay state, or
   IV counters; fence old incarnations. Keep `UNKNOWN`, refusal, timeout, crash,
   and confirmed disclosure distinct. Uncertain external effects remain
   `UNKNOWN` and do not authorize automatic retry. A memory graph may track
   opaque allocation ID, generation, length bounds, lifecycle state, and
   provenance for reconciliation. It is a projection, not authority: no secret
   bytes, live capabilities, or authorization decisions belong in the graph.
   Missing, null, non-finite, overflowed, stale, contradictory, or
   unauthenticated metadata blocks use/reuse.

The minimum discriminating runtime test pauses the loaded protected runtime
after verification and attempts to mutate the input through a retained alias.
It passes only if mutation is prevented or the operation refuses before any
consumer effect; duplicate promotion must also refuse. A TypeScript freeze or
mocked host status cannot prove protected-runtime isolation. On the selected
hardware/TEE profile, fault injection with adversarially false host telemetry
must show affected access refused before effects, region retirement, and no
silent reuse after restart. Such a test demonstrates only that target's
containment path, not universal correction, erasure, or malicious-firmware
resistance.

This is the useful middle ground: no general shadow copy of secrets, but one
bounded quarantine buffer and an explicit verify-before-effect/lease/retirement
protocol. It adds resource bounds and validation work and can fail closed under
load; no performance or complete-correctness claim is made without measurement
on the selected Fungi runtime and protected host. ECC status, authenticated
input, authorization, cleanup, and lifecycle audit are complementary controls,
not substitutes for one another.

### Caught provider refusal and terminal response sealing — TypeScript candidate only

Astra's first audit reproduced a provider-saved callback invoked by a
handler-controlled serialization getter: the late callback refused, but the
handler caught it and a 200 was published. RED/GREEN fixes now check the
monotonic request-failure latch after serialization and again in the outer
continuation; a queued microtask case also first reproduced 200 and now returns
500. Both pre-seal failures remain terminal.

Astra then found that an injected audit `commit`/`emit` hook could call and
catch the retained callback after the response latch check. Changing that
request to 500 after accepting an immutable 200 event would make the response
and audit evidence disagree. The kernel now performs one synchronous
failure/deadline arbitration and seals the selected response before invoking
audit hooks. A retained callback still refuses and cannot reacquire or re-enter
consumer code, but post-seal attempts cannot retroactively revise the matching
response/event. Tests cover both optional `emit` and required `commit`; this is
an explicit temporal contract, not a claim that arbitrary audit hooks are
trustworthy.

Independent Astra review found that `InMemoryAuditSink.commit()` enqueued the
event and then scheduled flush work; if scheduling threw, `handle()` returned
503 although the event was retained. A test-first regression reproduced
`503 / pending=1`. The built-in sink now defines bounded queue insertion as its
synchronous acceptance point; microtask/timer scheduling is best-effort export,
and scheduler failure cannot undo acceptance. If both schedulers refuse, the
event remains charged in the bounded queue. With capacity one, the next
reservation retries scheduling but still refuses before handler effects; after
the asynchronous drain and explicit `takeDrained()` custody transfer release
capacity, a subsequent request proceeds and its event drains normally. This
avoids synchronous flushing on the protected request path.

The generic injected `AuditSink` remains a trust boundary: its implementation
must honor the newly documented accept-or-not `commit` contract. The kernel
cannot prove that an arbitrary custom sink did not retain an event before
throwing; such sinks need their own authoritative outbox. The built-in fix is
not durability evidence: its retained queue is process memory and can be lost
on process termination.
